## Context
Goal: a working demo inside Serato DJ Pro on the user's Mac (M2/M3, DJ-SM9-class Serato setup) within a few hours — load a song from disk, connect the MPD226, trigger playback with at least one pad, all with Serato running and YuVi Glow loaded into an FX slot. This is the **first time this codebase has ever been compiled on macOS** — everything up to now has been built/tested on this Linux sandbox (Standalone + VST3 only; AU is macOS-only and has literally never been built).

## Decisions (from user Q&A this session)

1. **Pad playback fallback — real bug found while planning this**: currently, none of the 16 grid pads play anything unless they have a BPM loop region (only pads 0-3, only after tap-tempo/manual BPM entry) — and the only other way to bind a pad to "play the whole file" (the old single-pad "Learn Trigger Pad" button) was removed from the UI earlier in this same session, per an unrelated request. Without a fix, a freshly-mapped pad on the Mac would do nothing when pressed. **Fixed**: `YuViGlowAudioProcessor::triggerOrStopPadLoop()` (`Source/PluginProcessor.cpp`) now falls back to `triggerPlayback()` (whole file, restart-on-repress) for any pad without a loop region, instead of doing nothing. Pads 0-3 still switch to short beat-aligned loop behavior once BPM is established — this is additive, not a regression. Means the existing "Edit MIDI Mapping" flow alone (already fully built, no UI changes needed) is enough for the demo — no BPM/tap-tempo/libsonare involvement required on the critical path.
2. **Two new/renamed docs, kept deliberately separate** (explicit user requirement — mirrors `DEVELOPER_NOTES.md` vs `STANDALONE_INSTRUCTIONS.md`'s existing dev/usage split):
   - `DJ_INSTRUCTIONS_SERATO.md` (existing, unchanged name) — usage only, no build steps. Its old "Getting the plugin onto your Mac" placeholder now just points at the new doc.
   - `DJ_DEVELOPER_ONETIME_BUILD_SERATO.md` (new) — everything to go from a fresh `git clone` to YuVi Glow loaded and working in Serato: prerequisites, build, install, verify, troubleshoot. Self-contained rather than requiring readers to also open `DEVELOPER_NOTES.md` (that file stays Linux/Ubuntu-only, per its own existing scope).
3. **Build layout**: separate `build/debug/` and `build/release/` directories (not one dir with `--config` switching), with both sets of instructions living in the same new doc. This maps naturally onto a **single-config generator** (Unix Makefiles or Ninja) rather than the `-G Xcode` generator `plan/issues/09-macos-build-targets.md` originally assumed — recommended over Xcode specifically because it needs only Command Line Tools, not a full Xcode.app install, which matters under time pressure if Xcode isn't already on the machine (multi-GB download risk). Xcode generator is mentioned as an optional alternative (useful if they want to debug inside the Xcode GUI later), not the primary path.
4. **Standalone smoke-tested before Serato**: build+run the Standalone app first, load one of the repo's own CC0 test files, map a pad, confirm it plays — proves the Mac port (JUCE, libsonare, CoreMIDI, audio) works at all, in the fastest/simplest environment, before adding Serato/AU-hosting variables into the mix. If something's broken, this isolates which half broke.

## Two more decisions (mid-session)
- **Getting the code onto the Mac is the user's own responsibility** — nothing in this session gets committed or pushed by Claude; the user will `git push` today's work themselves whenever they're ready. The developer doc therefore doesn't hard-depend on `git clone` as step 1 — it starts from "however the code got onto this Mac, here's how to build it," with a clone snippet offered as one option among others (AirDrop, rsync, etc.).
- **VST2 question raised, resolved without a rename**: the user asked whether Serato might be VST2-only (this project builds VST3, not VST2 — VST2's SDK was pulled from public distribution by Steinberg years ago, so building it isn't a simple config flip). This exact question was already flagged as unverified in `plan/issues/08`/`plan/issues/14`. Resolution: **build both VST3 and AU as already planned, don't rename anything** — AU already covers Mac regardless of how the VST2/VST3 question resolves (Serato's supported AU on Mac for a long time, and this project already builds it automatically on Apple), and the cheap, definitive way to settle the VST3 question is just checking Serato's FX panel directly on the Mac (already step 0 below) rather than preemptively renaming every VST3 reference in the repo on an unverified belief.

## Other real risks flagged in the new doc (not blocking, but called out explicitly)
- **AU vs VST3**: `plan/issues/08`/`plan/issues/14` already flagged that Serato has historically been AU/VST2-only, not VST3, despite this repo's name — genuinely unverified. The new doc's step 0 is "check the FX panel, see what Serato actually lists" before assuming either format.
- **Code signing**: local-only use needs no paid Apple Developer account (`plan/issues/09`), but a plain Ninja/Makefiles build (unlike Xcode's build system) does **not** auto-apply even ad-hoc signing, and modern macOS can refuse to load an unsigned AU/VST3 into a host process. The new doc includes `codesign --force --deep -s -` as a normal expected post-build step, not just a troubleshooting fallback.
- **MPD226 device-name matching**: `MidiDeviceManager.cpp` classifies by case-insensitive substring match on `"mpd226"` — should carry over fine to macOS CoreMIDI since it's the device's own USB product string, but is genuinely unverified on real Mac hardware. Explicitly documented as non-blocking either way: if it shows up as "Custom MIDI Device (...)" instead of "Akai MPD226", MIDI-learn still works identically — classification only affects the default display name and preset auto-naming, not functionality.
- **Universal binary build time**: `CMakeLists.txt` defaults to `arm64;x86_64` (universal). The new doc recommends overriding to `-DCMAKE_OSX_ARCHITECTURES=arm64` for the demo build (their machine is Apple Silicon only) to roughly halve compile time, noting this trades away Intel-Mac portability for a build that's for today's demo only.
