# AGENTS.md

Instructions for any coding agent (Claude Code or otherwise) working in this repo.

## What this repo is
YuVi Glow: a JUCE-based instrument + DJ companion built primarily for the M-Audio Code 49, and equally for an Akai MPD226 (16 pads + first fader — same control surface, different brand). One codebase builds four targets — Standalone, VST3, AU (macOS only), and LV2 (Linux only) — so the exact same plugin runs in Serato (macOS, via AU/VST3), Mixxx (Linux, via LV2 — it has no VST/VST3 support at all, confirmed by inspecting the installed binary), any other VST3/AU host, or standalone with no host at all. Full design context lives in [plan/](plan/) — read `plan/00-overview.md` first, then [plan/00-OPEN_ISSUES.md](plan/00-OPEN_ISSUES.md) for what's still outstanding, then the numbered docs themselves in `plan/issues/` (each starts with a `[STATUS]` tag — see "Plan doc status tags" below, read that before trusting any plan doc's content at face value). Non-technical usage docs: [DJ_INSTRUCTIONS_SERATO.md](DJ_INSTRUCTIONS_SERATO.md), [DJ_INSTRUCTIONS_MIXXX.md](DJ_INSTRUCTIONS_MIXXX.md) (also covers other DAWs at the bottom), [STANDALONE_INSTRUCTIONS.md](STANDALONE_INSTRUCTIONS.md) (Linux dev usage). One-time build/install steps: [DJ_DEVELOPER_ONETIME_BUILD_SERATO.md](DJ_DEVELOPER_ONETIME_BUILD_SERATO.md) (Mac), [DJ_DEVELOPER_ONETIME_BUILD_MIXXX.md](DJ_DEVELOPER_ONETIME_BUILD_MIXXX.md) (Linux/Mixxx). ## Ground rules
- **Both macOS and Linux are real distribution targets, not just macOS with Linux as a dev sandbox.** Serato (the original motivating use case) is Mac/Windows-only, so that path needs macOS. But Mixxx — a real, free, cross-platform DJ app — hosts YuVi Glow on Linux via its **LV2** build (Mixxx has no VST/VST3 support at all — confirmed by inspecting the installed binary, not assumed), which makes Linux a legitimate end-user target too, not merely where development happens. See `plan/issues/13-linux-dev-testing.md` (dev loop), `plan/issues/14-serato-effect-workflow.md` (Serato), and `DJ_INSTRUCTIONS_MIXXX.md` / `DJ_DEVELOPER_ONETIME_BUILD_MIXXX.md` (Mixxx / other hosts). Don't build anything that only works on one platform without a real reason.
- **Never hardcode logic to one controller model.** All physical-control → parameter bindings go through MIDI-learn (see `plan/issues/02-midi-mapping-code49.md`), which is what makes the same code work unmodified with the Code 49's pads/fader *or* the Akai MPD226's pads/fader *or* any other class-compliant MIDI controller — the plugin just binds whatever note/CC the selected device actually sends. Don't add a Code49-specific or MPD226-specific code path; if a future feature genuinely needs per-device defaults, put them in a config file (e.g. `config/code49-default-mapping.json`), never in code.
- **Audio thread discipline**: no allocation, no file I/O, no blocking calls (including ML inference) on the audio callback thread. Stem separation, key/BPM detection, and thumbnail generation belong on background threads (see `plan/issues/01-architecture.md`).
- **Don't commit large binaries.** Stem-separation model weights and any bundled sample libraries must not be committed directly to git — see `plan/issues/05-stem-separation.md` and `plan/issues/11-open-questions-assumptions.md` for the download-on-first-launch approach and licensing constraints. Flag before adding anything over a few MB.
- **Don't fabricate licensing.** Applies to everything, not just audio: any sample audio (sax multisamples, demo tracks) must have a real, checkable royalty-free/CC0 source recorded in `plan/issues/11-open-questions-assumptions.md` or a `LICENSES/` file; any new **code dependency** must have its actual license checked (not assumed) and recorded in `CREDITS.md` at the time it's added, and must be compatible with this project's own license (see below) before it goes in — never invent, assume, or skip-and-batch-later.
- **Serato only hosts VST3/AU as audio effects (audio in → audio out), never as MIDI instruments.** Any plugin meant to load inside Serato must have an audio input (`IS_SYNTH FALSE`), even if its main job is triggering its own sample playback — see `plan/issues/08-serato-integration.md` and `plan/issues/12-mvp-v0.md` for how the MVP satisfies this while still reacting to Code 49 hardware. A true MIDI-instrument target (no audio in) can only ever be the standalone app, never something loaded inside Serato.
- **Plugins get hardware control by opening their own direct MIDI connection to the device** (CoreMIDI on macOS, ALSA on Linux — both handled transparently by `juce::MidiInput`), not by relying on host-forwarded MIDI — Serato doesn't reliably forward hardware MIDI into effect plugins, but the OS MIDI layer allows multiple simultaneous listeners on one source, so the plugin can listen to the controller directly alongside Serato (or, on Linux, alongside nothing — there's no Serato there) without conflict.
- **Follow the phase order in `plan/issues/10-roadmap.md`** (currently reprioritized by `plan/issues/12-mvp-v0.md`). Don't jump ahead to stem separation or the sax engine before the current MVP is working end-to-end — each phase has its own approval checkpoint with the repo owner before implementation starts.

## Project license: AGPL-3.0 — this is a real constraint, not paperwork
This project is licensed **GNU AGPL-3.0** (see `LICENSE`, reasoning in `plan/issues/17-project-licensing.md`). This wasn't an arbitrary choice: **JUCE itself is dual-licensed AGPLv3 / paid-commercial**, so every build of this plugin already sits on one side of that fork regardless of anything else the project does. AGPL-3.0 was picked because the explicit direction was to go FOSS as far as possible rather than pay for a commercial JUCE license.

What this means day to day:
- **Every new dependency needs an AGPL-3.0-compatible license** before it goes in — permissive (Apache-2.0/MIT/BSD) and GPL-family are fine; anything with a non-commercial-only or no-derivatives clause is not. This is exactly why `libsonare` (Apache-2.0) was chosen over the more established but GPLv3 beat-tracking libraries (BTrack, aubio, Gist) in `plan/issues/16-beat-detection-and-loop-pads.md` — don't reverse that choice without re-reading the reasoning there.
- **Every dependency and credited asset goes in `CREDITS.md` when it's added** — not batched up later, not skipped because it feels minor.
- **One real open item, not yet resolved**: a JUCE forum post (not JUCE's own authoritative page) suggests AAX/AUv3/VST2/iOS builds specifically might not be coverable under AGPL even for open-source projects, meaning some of this project's own target formats could need a commercial JUCE license regardless of this project's own AGPL choice. Flagged in `plan/issues/17`, not settled — check `https://juce.com/legal/juce-8-licence/` directly (the authoritative source) before treating "fully FOSS, no commercial license needed" as certain for every format this project builds (VST3/AU/Standalone).

## Build
CMake + JUCE via `FetchContent` (pinned tag, see `CMakeLists.txt`). Xcode generator on macOS (`plan/issues/09-macos-build-targets.md`), Unix Makefiles/Ninja on Linux (`plan/issues/13-linux-dev-testing.md`). Formats: VST3 everywhere, AU macOS-only, LV2 Linux-only (Mixxx's actual hosting format — it has no VST/VST3 support at all, confirmed by inspecting the installed binary), Standalone everywhere (the Standalone build is the fast local dev-loop on Linux, since there's no Serato here to load a VST3 into). For exact commands (build/clean/run on Ubuntu) see [DEVELOPER_NOTES.md](DEVELOPER_NOTES.md) — keep it in sync with `plan/issues/13-linux-dev-testing.md` if either changes.

**Compiling on macOS and loading in real Serato has NOT been verified as of the last update to this file** — only Linux builds have been smoke-tested. Don't report a build "done" without one of: an actual macOS compile + Serato load test, or an explicit note that it's still unverified on the real target. See `plan/issues/12-mvp-v0.md`'s "Known limitation" section and `plan/issues/19-serato-mac-demo.md` / [DJ_DEVELOPER_ONETIME_BUILD_SERATO.md](DJ_DEVELOPER_ONETIME_BUILD_SERATO.md) for the active push to close this out.

## Claude Code skills to use while working here
- **`/run`** — build and actually launch the plugin (or a throwaway JUCE AudioPluginHost/standalone harness) to verify a change works, not just that it compiles. Prefer this over claiming something works from reading the code.
- **`/simplify`** — run after finishing a feature, before calling it done: cleanup pass for reuse/simplification in the DSP and UI code.
- **`/security-review`** — run before any build gets distributed to another person (Phase 5 packaging, or sooner if sharing a build ad hoc).
- These are invoked via slash command or the Skill tool; don't skip straight past them just because the task feels code-only.

## Code style
- C++20.
- JUCE naming/style conventions (PascalCase classes, camelCase members, `juce::` namespace usage as JUCE itself does).
- Prefer JUCE's own DSP/utility classes (`juce::dsp::FFT`, `juce::Synthesiser`, `juce::AudioThumbnail`, etc.) over reinventing them.
- **Organize like a human would: reusable components, no giant monolithic files, but don't over-abstract.** When the same pattern gets written out 2-3+ times (it happened with pad/fader/knob MIDI-learn logic — three near-identical copies before `Source/MidiLearnBank.h` existed), extract it into its own small, concrete class, not a generic framework. When a file is accumulating genuinely distinct responsibilities (audio callback + MIDI device connection management both used to live in `PluginProcessor.cpp` before `Source/MidiDeviceManager.h/.cpp` existed), split by responsibility. Keep the processor's public API stable across such refactors — UI components shouldn't need to change just because internals got reorganized.

## Test/dev assets
`assets/audio/royaltyfree/` holds small CC0 audio files for exercising file loading/playback in tests — not a curated end-user demo pack (that's still open, `plan/issues/11` item 8). Every file in there needs its license verified on the actual source page (not assumed) and recorded in that folder's `LICENSES.md`, per the "don't fabricate licensing" rule above.

`assets/WARNING_NON_FREE/` is the opposite case: a git-ignored drop folder for real, non-free/unverified test audio (e.g. songs given for local dev testing) that must never be committed — `.gitignore` excludes everything in it except its own `README_WARNING_NON_FREE.md`, which explains the rule. See that README before adding anything there.

## Plan doc status tags
`plan/00-overview.md` and `plan/00-OPEN_ISSUES.md` are the only files directly under `plan/`; every numbered doc (`01`-`19` and beyond) lives in `plan/issues/`. `00-OPEN_ISSUES.md` is a generated-by-hand index of every doc that's not `[COMPLETED]`, grouped by tag — regenerate it (or at least re-check it) whenever a doc's tag changes, and when adding a new numbered doc, add it there too if it's not immediately `[COMPLETED]`.

Every file in `plan/issues/` starts with a `**Status: [TAG]**` line right after its title, one of:
- **`[PLANNED]`** — written up, no real work done beyond the markdown itself.
- **`[DEVELOPED]`** — real code exists and works, but the doc's scope isn't fully complete (something's still outstanding — a verification step, a follow-up piece, etc.).
- **`[COMPLETED]`** — everything the doc describes is built and verified. Nothing outstanding.
- **`[UNRESOLVED]`** — has genuinely open questions or deferred work that need a real answer later (hardware verification, a licensing check, a decision only the repo owner can make) — distinct from `[PLANNED]`, which just means "not started," and from `[DEVELOPED]`, which means "started and mostly working."

Keep these current: when a `[PLANNED]` doc gets built, bump it to `[DEVELOPED]` or `[COMPLETED]` in the same pass — don't leave it stale for a future session to catch. When you create a new plan doc, give it a tag from the start.

## Feature requests vs. planned issues
`plan/issues/` is for work that's already accepted into the roadmap — even if not started yet, it's understood to be *the* plan. If something TRULY seems like a totally new feature — not a refinement of existing scope, not something already implied by `plan/00-overview.md` — it does not belong there. Put it in **`plan/feature-requests/`** instead, as `rfcNNN-<slug>.md` (three-digit, zero-padded, sequential — `rfc001-...`, `rfc002-...`). Near the top of the file, recommend a branch name for if it's ever built: `feature-RFCNNN/<name-of-feature>`, matching the file's own number. A feature-request doc does **not** get linked from `plan/00-overview.md` or `plan/00-OPEN_ISSUES.md` — those only index accepted work — until/unless the feature is actually decided on and the doc (or its content) moves into `plan/issues/`. See `plan/feature-requests/rfc001-yuvi-rays-dvs-midi-integration.md` for a worked example.

## Scope discipline
Don't add speculative features, alternate DAW targets, or abstractions beyond what the current roadmap phase calls for. If something in `plan/` looks wrong or outdated once real hardware/code exists, update the relevant `plan/*.md` file rather than silently diverging from it.
